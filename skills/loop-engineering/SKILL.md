# Loop Engineering — 定时与持续任务

本 skill 为已授权的周期任务组织检查、补救和续接，不提供独立调度 runtime。共同行为见 [执行契约](../production-governance/references/workflow-contract.md)，能力与路径见 [宿主适配](../production-governance/references/host-adapters.md)。

## 使用边界

| 请求                                         | 处理                                       |
| -------------------------------------------- | ------------------------------------------ |
| `/auto 把这个 bug 修好，直到完成`            | 当前任务持续推进，不创建调度               |
| `/auto 把覆盖率提到已确认的目标`             | 当前任务与适用验证，不凭“提到”开启 loop    |
| `/auto 5m 检查 CI，全部结束后停止`           | 明确间隔与目标，检查调度条件               |
| `/auto 持续巡检服务，失败时执行已批准的恢复` | 明确持续需求，登记节奏、恢复范围与退出方式 |
| 单次任务完成后看起来适合长期维持             | 完成本次任务，不自行转为后台巡检           |

仅有“自主”“自愈”“达到”“直到”等词不构成周期任务授权。一次 run 内的修复反馈使用原工作流；I/O 自验证可参考 feedback-loop。

## Step 1：确认周期契约

先从用户请求、此前有效授权与项目设置中确定以下条件。已有答案直接采用，只有影响调度的关键缺口才澄清；在等待必要答案时可先做一次已授权检查。

| 条件       | 必须记录的事实                                                      |
| ---------- | ------------------------------------------------------------------- |
| 目标与模式 | 定时巡检、达成目标即停、持续维持；具体服务/仓库/对象                |
| 间隔       | 用户/项目给定的正数 `s` / `m` / `h`，及宿主支持范围；没有通用默认值 |
| 每轮权限   | 只读检查，或明确列出的修复动作；外部通知仍需发送授权                |
| 停止条件   | 达成、用户取消、明确到期或适用预算限制；长期维持须有可操作取消方式  |
| 预算       | 仅记录已明确的迭代/时间/费用上限；缺遥测为 unknown，不自行授权费用  |
| 恢复依据   | 用户基线、当前工作归属、必要恢复材料及其覆盖范围                    |

不要求先提交代码，也不依赖 hook 必然运行。预算到期不能自动重启或扩额；任何用户给出的“无限”也不取消目标、权限、取消与验收约束。

## Step 2：定义 DOER 与 CHECKER

在 `.auto/runs/<loopId>/loop-contract.md` 写入检查目标、适用验收、允许动作和停止条件。loopId 使用首轮 runId，各轮通过 correlationId 关联；loop-contract/state/summary 是派生记录，不新增协议对象类型。

**CHECKER** 判断当前状态是否满足已确认的规则：

1. 先有独立期望来源，例如用户验收、仓库测试要求或实际 CI 检查集合。
2. 运行真实命令或读取可靠状态，保留命令自身退出码、输出、对象版本和时间。
3. 对测试检查发现数、执行数、skip、失败与回归；对 CI 区分 pending/cancelled/failed/passed，并核对是否针对当前提交。
4. 对覆盖率/延迟等指标记录样本和适用阈值；缺报告、空测试、全 skip、过期证据不得判达成。

退出码 0、命中 `passed` 正则、文件存在或自评分均不足以单独证明收敛。高影响任务按共享契约补 A/B/C 三链；本地可写记录只证明本地一致性。

**DOER** 只在 CHECKER 发现有授权且可行动的问题时执行：增量 SCAN → 必要 PLAN → 最小修改 → 适用 VERIFY。用户只授权监控时，记录状态与可选建议，不自行修复或发布。

## Step 3：核验调度能力

先检查当前工具 schema、版本、权限、生命周期和取消接口，记录 `supported | unavailable | unknown` 及依据。不能凭宿主名称假定支持或不支持某个工具。

| 实际能力         | 可声明的行为                                                     |
| ---------------- | ---------------------------------------------------------------- |
| 会话内定时工具   | 按真实接口唤醒；说明会话结束后的限制                             |
| 已确认的持久调度 | 仅在创建成功后记录任务 ID、下一次执行、生命周期与取消方法        |
| 只有当前会话等待 | 可在会话内等待；不能称持久后台运行                               |
| 无适用调度       | 完成当前授权检查并说明缺口；不伪造任务，不擅自安装外部 cron/服务 |

外部调度工具也须符合原授权和当前环境，不因内置能力缺失自动新增服务。只有真实创建成功才写 `scheduled`；失败记录错误，不能写“正在后台运行”。

每次唤醒携带同一 loopId 和目标引用，读取累积预算、取消状态、上轮证据及遗留事项，不能重置迭代状态。间隔按用户要求执行，不擅自改成随机偏移或其他默认节奏。

## Step 4：单轮执行

1. 读取当前状态，核对用户取消、到期、预算与实际目标版本。
2. 防止同一目标的并发写入；上一轮仍在运行时按真实调度能力跳过/合并后续 tick，记录原因。
3. 先运行 CHECKER。状态未变或已满足要求时，不为消耗一次 tick 强制重跑实现流程。
4. 有可行动且获授权的问题再执行 DOER；无权限或关键外部依赖缺失时记录阻塞，继续仅被授权的观察。
5. 修改后重新运行相关验证，当前证据绑定最终产物。检查交付状态与归属，clean-state 不要求 Git 干净。
6. 原子或以宿主支持方式可靠更新 loop-state，保留原始输出与当前 run 证据引用。

状态记录示意（实际值必须来自当前任务）：

```json
{
  "loopId": "<首轮 runId>",
  "goal": "<用户确认的目标>",
  "mode": "<monitor | convergent | sustain>",
  "interval": "<已确认间隔>",
  "iteration": 1,
  "status": "<running | scheduled | blocked | completed | cancelled>",
  "scheduler": {
    "support": "<supported | unavailable | unknown>",
    "taskId": null,
    "lifecycle": "<实际支持范围>"
  },
  "budget": { "source": "<用户/项目条款或未指定>", "spentUsd": null },
  "evidenceRefs": [],
  "nextAction": "<当前可执行步骤或阻塞原因>"
}
```

这里的 null 表示尚无对应值或遥测，不代表费用为零；未创建任务时 taskId 必须保持空值。

## Step 5：收敛与停止

- 目标收敛模式：必要验收有当前证据且无 fail/pending 时停止；不能为刷次数继续改动已完成目标。
- 监控/持续维持模式：一次健康检查不等于长期任务完成，按已确认期限或取消条件继续。
- 用户取消、授权预算/时间到期：停止执行并取消本任务拥有的后续调度，不自动重启。
- 同一路径连续两轮无进展：重新调查、换验证/候选或明确当前阻塞；不循环执行相同动作来碰运气。
- 指标回退：先检查采样、外部变化和本轮 diff；只撤销归属明确且需要撤销的本轮变更，归属不明保留现场。禁止仓库级 reset 或以单一分数自动回退。

终止时确认取消操作的真实结果，写 loop-summary 与必要 session-continuity：轮次、达成/未达成、证据、实际成本或 unknown、剩余风险、下一步。调度取消失败也应报告，不能仅把本地状态改为 completed 就宣称后续 tick 已消失。

不自动 commit、push、发布或清理用户工作树。缺证据允许失败/部分完成总结，不用无限 Stop 阻断制造全绿。

## Step 6：跨迭代学习

- 只将有证据的新失败模式、有效策略或规则冲突提炼成 LearnCard，查重后合并到 insights。
- 一次指标上升不足以证明策略有效；没有对照或因果依据时保留假设标签。
- feedback 按 runId 幂等更新，unknown 不进成功率分母。参见 knowledge-management 的反馈契约。
- 后续 SCAN 读取相关遗留与经验，不重复加载全部历史与所有 skill。

## 验收场景

- “把测试修到通过”：持续当前修复，不创建每十分钟任务。
- “每五分钟查 CI”，真实调度不可用：报告当前检查与能力缺口，不生成虚构任务 ID。
- 测试命令 exit 0 但发现 0 个测试：未达成，检查测试发现配置。
- 本轮失败数上升，同时用户加入了新测试：调查变化来源，保留用户修改，不自动 reset。
- 用户取消时删除调度失败：停止主动续建，报告真实未取消状态与可执行处理步骤。
- 未提供费用遥测：记录 unknown，不宣传零成本，不填入默认美元预算。
