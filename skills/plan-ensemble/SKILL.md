# Plan Ensemble — 视角集成规划

多个视角可以暴露不同风险，也可能重复同一错误。收益取决于任务、隔离和验证，不能由代理数量、投票或论文平均结果推断。共享语义见 [执行契约](../production-governance/references/workflow-contract.md)，工具支持见 [宿主适配](../production-governance/references/host-adapters.md)。

## 使用时机

以下情况值得评估是否需要本 skill：

- 用户明确要求独立视角或多计划对比。
- 高复杂度任务中，查过代码与关键事实后，架构、迁移或恢复方式仍存在决定性分歧。
- brainstorming 的真实候选各自覆盖不同风险，单个验证探针不足以判断。

默认单执行者。仅有“重构”、多个模块或多条路径不自动触发委派。简单任务、用户已确定方案、没有可独立分析的问题，或当前资源不足时，保留单计划与必要反例即可。

## 激活前核验

1. 明确需要独立视角解决的具体分歧，以及它如何影响用户目标。
2. 核对当前用户/项目授权和宿主能力；技能方法本身不覆盖更高层的委派限制。已有有效授权无需再问。
3. 判断是否能裁剪成互相独立的只读任务，且协调成本合理；未取得成本遥测时写 unknown。
4. 记录执行方式：真实独立代理 / 主执行者多视角分析。后者可用，但必须标明没有独立性，不能伪称多代理验证。

## 核心流程

### 1. 合成者先独立立论

在读取其他草案前，写下自己依据用户目标形成的计划要点、关键假设和需要查证的问题。这能保留独立比较基线，但不保证降低某个固定比例的错误率；已经读过草案就如实记录，不能倒填“独立稿”。

### 2. 按失败模式选择视角

通常两到三个视角足够，按实际分歧选择，不为凑数量或形式对抗增加代理。

| 视角       | 关注点                                     | 适用信号                 |
| ---------- | ------------------------------------------ | ------------------------ |
| 最小变更   | 复用已有机制，以最小必要 diff 完成全部验收 | 波及面较大、已有成熟实现 |
| 演进与兼容 | 兼容当前契约，评估已有依据的后续需求       | 平台边界、版本迁移       |
| 风险与恢复 | 失败范围、归属保护、独立恢复与验证         | 数据迁移、生产变更       |
| 性能       | 真实延迟/吞吐/容量预算与测量方式           | 明确性能目标             |
| 安全       | 权限边界、输入、密钥与攻击面               | 已识别安全风险           |
| 运维       | 可观测、诊断、取消、降级与故障恢复         | 后台服务、长任务         |

不以“六个月后也许需要”为由默认扩大范围；最小变更也不能通过留下必要验收未完成来缩小 diff。

### 3. 只读出案与上下文隔离

使用实际可用的代理工具及其 schema，不假定 Claude/Codex 存在固定 API。每个 worker 只收到：目标原话、必要文件与事实来源、约束/授权范围、视角、验收和输出位置；不重新运行主入口控制流程。

发散期不互传草案，保留独立来源。只读规划可共享仓库；若后续并行实施，按 using-git-worktrees 的条件隔离写入，不把规划授权误当任意修改授权。

草案保持简短，通常不超过约 30 行，但必要证据不能为行数上限删掉：

```markdown
## 视角：<名称>

- 目标与依据：<用户条件、文件或规则>
- 拆解：<关键步骤及依赖>
- 取舍：<采用/放弃理由，事实与假设分开>
- 风险与反例：<失败条件及验证方式>
- 成本与未知：<触及范围、依赖、恢复；无遥测的成本标 unknown>
```

### 4. 处理分歧并合成

1. 列出结构性分歧及对应依据。草案一致就记录一致，不强造分歧。
2. 对照目标覆盖、风险/恢复、实施成本、当前兼容性逐项比较。可用表格；自评分不是实测，不用加总分或多数票直接判定胜者。
3. 对决定性冲突查证代码、正式规则或小型实验。少数意见和多数意见都须经同样的证据检验。
4. 选择有依据的主计划，吸收其他草案中相容的局部改进，说明来源与取舍；不要拼接互相矛盾的假设。
5. 产出唯一 QuestMap，仍未确认的关键用户选择按 requirement-clarifier 处理。已授权技术细节直接决定并写回。

默认一轮出案与一次合成。只有新的决定性未知项才追加调查；同一分歧反复辩论而无新证据时，改变验证方式，不继续堆代理。

## 产物与集成

- 将重要分歧、假设和决定写入 QuestMap.pitfalls / alternatives / decisionNotes。
- 实际使用多草案时，可将草案、证据和合成过程放 `.auto/runs/<runId>/plan-ensemble.md`，由唯一 QuestMap 引用，不复制整个 run。
- 代理结论是待验证输入；owner 负责后续集成验收，不能把草案一致性当执行成功。
- LEARN 记录真实发现与失败模式。无对照实验不声称“该视角胜率更高”或比单执行者更快。

## 验收场景

- 小范围函数重构：单计划与回归即可，不因策略标签创建代理。
- 高风险数据迁移已有委派授权：选择恢复与兼容视角，独立出案后通过恢复实验解决分歧。
- 用户要求多角度，但本机无代理工具：主执行者显式多视角分析，注明未隔离，不伪造 agent ID。
- 三份草案一致但正式 API 约束相反：以独立契约为依据修正计划，不能靠多数票放行。

## 验收标准

- [ ] 记录实际分歧、采用该方法的理由与委派依据。
- [ ] 上下文与写入边界明确，独立性声明符合实际执行。
- [ ] 候选比较引用事实；关键决定不依赖代理数量或自评分。
- [ ] 最终只有一个 QuestMap，未验证假设仍显式保留。
- [ ] 没有把单次任务或外部研究的结果宣传为普适收益。
