# Requirement Clarifier — 需求澄清

目标是消除会导致错误交付的未知项，同时保留已授权任务的推进能力。遵循 [共享执行契约](../production-governance/references/workflow-contract.md) 的目标、事实与授权规则。

## 使用时机

以下信号用于检查信息缺口，不是必须提问的关键词：

| 信号                     | 先检查的依据                               |
| ------------------------ | ------------------------------------------ |
| “完整”“快”“看起来”等表述 | 用户前文、现有产品行为、项目验收与设计规范 |
| 关键名词含义不清         | 领域模型、接口契约、相邻实现与测试         |
| 多种合理实现路径         | 既有技术栈、用户选择、可逆性与维护成本     |
| 验收条件缺失             | 真实复现、业务规则、已确认的目标行为       |
| 范围或优先级冲突         | 原始任务、outOfScope、当前有效授权         |

只有在查证后仍有关键缺口，且不同答案会改变正确性、产品行为、授权范围或重大成本时，才向用户澄清。技术细节可以有依据地决定，写明假设即可；发布、发送消息或任务外破坏操作仍须真实授权。

## 核心流程

### 1. 先从上下文解决

1. 保留 `RouteDecision.userIntent` 中的原始任务，检查本轮及此前有效授权。
2. 查项目规范、相关代码/文档、已接受方案与验收来源；不要让用户重复提供已有信息。
3. 将未决项分为：已确认事实、可逆且有依据的实现选择、影响结果的关键未知项。
4. 对前两类自主推进；对关键未知项准备最小问题，继续不依赖答案的检查或实现工作。

例如“优化首页性能”已有复现及延迟预算时，可直接定位与验证；只有产品优先级仍冲突时才询问。“加登录”若仓库已有统一认证契约，先遵循契约；全新产品的目标用户与认证方式都无法判断时才澄清。

### 2. 必要时提出少量问题

- 默认只问最关键的一题，单次最多三题；优先范围/验收，其次不可逆技术约束。
- 给出短问题、可比较的选项与有依据的推荐，不使用预设答案诱导用户接受。
- 使用当前宿主实际提供的提问能力，遵循其 schema 与可用模式；不假定 `AskUserQuestion` 或其他工具存在。普通文本提问也应说明哪个缺口影响结果。
- 不把可选建议包装成权限要求。已有授权不重复询问，不因自动检查建议重新设置审批。
- 可选问题未获答复时，说明合理假设后继续；必需答案缺失时仅暂停依赖步骤。等待时间本身不是答案或授权。

### 3. 写回计划

将问题、事实来源、用户答案或采用假设写入 QuestMap 的 assumptions / decisionNotes，并保留原始 userIntent。记录较长时可使用 `.auto/runs/<runId>/clarification-record.md`，不为零问题任务强制新建文件。

```markdown
- 未决项：<具体缺口及影响>
- 已查依据：<会话约定 / 项目规范 / 代码或测试>
- 处理：<直接采用已有规则 / 带假设推进 / 需要回答>
- 答案或假设：<用户原意或推断，不能混为已确认事实>
- 计划影响：<验收、范围、依赖步骤如何变化>
```

## 与其他 skill 的分工

| Skill                 | 用途                               |
| --------------------- | ---------------------------------- |
| requirement-clarifier | 消除尚未解决的关键产品/验收缺口    |
| brainstorming         | 对真实架构取舍给出有证据的方案推荐 |
| research-analyst      | 从代码、文档和外部资料查证技术事实 |
| prd-writer            | 用户需要正式需求文档时整理完整需求 |

不要求四者依次全部运行。PLAN 中发现缺口就处理；EXECUTE 出现新证据时也可更新假设。LEARN 仅记录可复用的新澄清经验。

## 验收场景

- “看起来排版乱了”，仓库已有样式规范：直接按规范修复与检查，不因“看起来”提问。
- 用户已选 Redis，后来要加入缓存：沿用已确认方案，不重新问 Redis/内存/数据库。
- 现有会话没有定义导出用户数据的可见范围，选择会影响权限：只澄清该关键边界，继续独立的数据结构检查。
- 修复需新增关联测试或锁文件：记录 scope-expand，不重复请求已授权的实施许可。
- 用户未回答可选配色偏好：采用项目默认并说明假设；不能把未回复视为发布授权。

## 验收标准

- [ ] 每个问题都对应查证后仍未解决的关键缺口。
- [ ] 没有重复询问已经明确的用户选择与授权。
- [ ] 可逆实现选择有理由；假设与用户答案分开记录。
- [ ] 原始任务保留，QuestMap 根据新信息更新。
- [ ] 必需问题只暂停依赖步骤，可独立工作继续推进。
